01 · 定义

什么是 agent 的可观测性

可观测性指系统在运行之后留下的记录，足以回答三个问题：发生了什么、为什么发生、此刻处于什么状态。前两个是事实与因果，第三个是当前态。三者缺一，结论就变成猜测。

agent 与传统服务的观测对象不同。无状态服务的观测单位是请求：进来一条、出去一条，成不成看状态码。agent 的单位是一段执行过程 —— 一次对话、若干轮模型调用、成串的工具执行、随时可能发生的用户介入。这些内容一半在内存里，一半在磁盘上，还有一部分在外部世界：被修改的文件、调用过的接口。外部副作用无法重放，所以记录必须足够细，细到能解释「当时为什么这么做」。

准备实现 agent 的人，在写第一行业务代码之前需要定三件事：事实记在哪里、谁有权读取、凭什么相信它。这三件事决定了后面所有界面与协议的形状。

02 · 前置

为什么观测必须先于界面

界面是投影。既然是投影，就必须有一个可以回退的源头：投影看起来不对时，能回到源头判断是渲染错了，还是执行真的如此。没有源头，界面就是唯一真相；一旦它出错，就没有第二个人能证明它错了。

第二个理由是时间。agent 的一轮执行可以持续数分钟到数小时，期间进程可能被关闭、宿主可能重启。如果状态只活在内存里，重启之后没人说得清上一轮做到哪一步 —— 是模型超时，还是工具执行到一半被打断。能把状态从记录里重建出来，是长时执行的前提，不是可选项。

第三个理由是消费者不止一个。同一段执行过程，界面要读它来渲染，编辑器协议要读它来转发，记忆系统要读它来沉淀，定时任务要读它来判断上一次是否完成。每个消费者都需要事实；如果各自维护一份，迟早互相矛盾，而矛盾发生时没有任何一方有裁决权。

一份事实，多个投影。

03 · 事实源

事实源：一条追加式的事件流

3.1 追加写而非快照

事实源有两种形态：快照与事件流。快照只保留「现在是什么样」，事件流保留「怎么变成这样」。前者省空间，后者能回答原因。

选择追加写的理由不在于日志好看，而在于可重建：当前状态是事件序列的一个函数，随时可以重算；任何一次投影出错，都可以用同一份输入重新算一遍。代价也很直接 —— 数据只增不减，读取需要策略，截断需要小心，这些后面单独说。

追加写还有一条隐含要求：一次写入要么完整落盘，要么完全不落。半条记录比没有记录更糟，它会让读者把残缺当成事实。

3.2 事件分几类

事件分类不需要按业务划分，按「重建状态需要什么」划分即可。五类齐全，过程就能还原：

事件流的五个维度
维度 记什么 回答什么
输入 用户消息、定时触发、对端投递 这一轮因何而起
动作 模型请求、工具调用、审批发起 做了什么
结果 工具返回、错误、被拒绝 结果如何
边界 回合开始与结束、运行开始与结束 一段执行从哪到哪
决策 审批结论、模式变更、策略调整 为什么这么做

缺哪一类，对应的那个问题就无法回答。只有动作没有边界，读者分不清两轮执行；只有结果没有决策，读者看得见「越权执行」，却看不出是谁批准的。

3.3 因果

事件之间必须有显式的因果引用：这条结果属于哪一次调用，这次调用属于哪一轮，这一轮由哪条输入触发。靠时间戳相邻去推断是行不通的 —— 并发执行时两条事件可能落在同一毫秒，顺序只在文件里，不在时间里。

因果引用还有一个附带好处：它让分支成为可能。同一段历史可以被分叉成两条路径，各自的后续事件指回同一个祖先，读者据此知道它们是同源的，而不是重复记录。

3.4 单一写者

一份事实流只能有一个写者。写者多于一个时，编号会冲突、顺序会错乱，而读者无法区分「同一件事被记录了两次」与「同一件事真的发生了两次」—— 这两者的区别，恰恰是排查时最需要的信息。

多宿主场景下只有两条路：把写入串行化到一个所有者，或者各自留一份事实、由上层按标识合并。前者要求所有权可判定（谁是当前写者、失效后如何接管），后者要求事件带全局唯一标识。两条都不便宜，所以应当在引入第二个宿主之前决定，而不是之后。

04 · 投影

投影：同一份事实的多个视图

4.1 投影只读

投影是事实的某种呈现：界面、协议通知、统计数字、索引。它们可以有各自的缓存与格式，但不能反向改写事实。一旦视图能写回，事实就被界面状态污染，之后再拿它当判据就没有意义 —— 你无法区分「执行真的失败了」与「界面上被标成了失败」。

4.2 增量读取

消费者需要的是「从哪继续」，而不是「全部重来」。游标是契约的一部分：它由事实源的标识序列定义，必须单调、可比较、在重启后依然成立。没有游标，每个消费者都要全量扫描，成本随历史线性增长，长会话会先拖垮界面，再拖垮一切。

4.3 预算与截断

读取必须有上限：字节数、条数、时间窗。上限带来一个副作用 —— 读者会看不到中间的一段。这时最危险的不是缺失，而是缺失被误读为「没有发生」：界面读了几百条就以为历史只有几百条，统计按窗口截断就得出「今天没跑过」。

所以截断要在数据上留痕：告诉读者「这里被截断了、还有更多」，而不是安静地少给一段。

4.4 读态与事实分离

已读位置、展开收起、滚动偏移，这些是消费者的状态，不是事实。把它们写进事实源，事实就会随界面操作变化：同一条历史在两个界面上显示不同的「状态」，而两者都不是执行的真实情况。

分离之后还有一个好处：事实源可以按内容设计，只关心「发生了什么」，不必迁就任何一个界面的需要。

05 · 信号

状态信号与分级

5.1 事实与聚合

事件流负责细节，聚合负责「现在怎么样」：是否在运行、这一轮用了多少、文件改了多少。聚合可以从事实算出来，但不必每次现算 —— 允许缓存，前提是缓存失效时以事实为准，而不是以缓存为准。

聚合最容易出的问题是被当成事实：界面相信了聚合里的「运行中」，而事实流里早已写下结束。判断分歧时，结论永远从事实得出。

5.2 级别是筛选策略

调试、信息、警告、错误这些级别，是「保留多少细节」的筛选开关，不是重要性排序。一次正常的工具调用在调试级别是细节，在事故复盘时是关键证据；反过来，绝大多数警告在正常情况下确实可以忽略。

设计上的取舍只有一条：生产环境保留「能重建状态的最小集合」，其余按需打开。把级别当成重要性排序，会导致真正的证据被过滤掉，留下的全是噪音。

5.3 观测的所有权

观测能力属于执行方，而不只属于运维方。执行 agent 的进程应当能读自己的记录：读到本轮做到哪、上一次工具调用返回了什么、哪个环节在重试。把这份能力交回执行方，排查不必依赖外部工具链，也避免了「只有开发者能看到真相」的结构。

06 · 失效

可观测性会在哪里失效

四类失效，都不来自「没记」，而来自「记了却读不懂」。

6.1 静默

没有回执的通道最危险：单向通知、事件推送、异步回调，丢一条不会产生错误码。于是「还没发生」与「已经丢了」在观测上完全不可区分，界面只能维持上一个状态，看起来像卡住。

对策不是加更多日志，而是让每条通道自带可验证的完整性：序号、心跳、结束标记。有了这些，「停在某处」才能被判定为异常，而不是被当成还在进行。

6.2 中间态

状态在切换过程中被读取，会得到一个从未存在过的值。例如一次运行已经结束，但标志位尚未归位，此刻按「是否在运行」现算，输出就是「仍在运行」。这类错误的特征是：日志正确、读取正确、时间也正确，只是读的时机不对。

做法是让知道语义的一方给出已确定的状态，而不是让读者去猜一个瞬时值。语义在事件里，不在字段里。

6.3 重复

同一件事被记录两次，读者无法分辨是重放、重试，还是真的做了两遍。成因通常有两个：写者不唯一，或者一次触发被两条路径各处理一次。

识别手段依然是标识：一件事一个唯一 id，写入前先认领，重放时能看出「这条已经记过」。没有唯一标识的重复，事后只能靠内容比对，而内容往往相似到无法比对。

6.4 时间

时间戳看似客观，实则充满假设：时钟会回拨，时区会跨日，「今天跑了几次」依赖本地日历。用时间做唯一判据的观测，在多时区或长时间运行后必然出错。

稳妥的做法是把时间当辅助证据：判断先后靠序列，判断间隔靠绝对时间，判断「今天」交给上层明确按哪个时区计算。

失效几乎都不在记录端，而在读的一端。

07 · 方法

排查方法论

7.1 顺序

先确认事实源完整，再怀疑投影。顺序反了，就会在渲染层反复找问题，而根因在写入端：条目缺了一段、顺序错了、两条同号。判断完整性的三个检查 —— 条数对不对、顺序是否单调、因果引用是否闭合。

7.2 复现优于推断

读代码能提出假设，只有复现能给出结论。用真实入口驱动：协议客户端发一次请求、脚本跑一次完整回合，看记录里多了什么、少了什么。这一步省不掉，省掉就会把「我认为」写成「已验证」。

7.3 结论的形态

结论应当能落到具体证据上：哪一条记录、哪一行的原文、哪一个标识。落到具体位置的结论可以被别人复核；落到「应该如此」的结论只能被相信，不能被检验。

08 · 代价

代价与边界

8.1 体积

追加写的增长是线性的，没有上限的系统会在某一天突然不可用。截断与轮转要保住两样东西：因果与边界。按时间切分最省事，但会把一段执行切成两半，读者看到「有结果没有开始」。按边界切分才安全。

8.2 隐私

记录越全，泄露面越大。日志里会出现路径、命令、凭据的痕迹与用户的原始输入；这些字段该不该落盘、谁能读、保留多久，属于信任模型的一部分，应当与权限设计一起决定，而不是事后补救。

8.3 开销

观测不能成为执行路径上的负担。每条同步写入、每次强制落盘，都会把延迟带进用户感知的环节。可行的做法是把写入放在执行的关键节点（边界、结果、决策），而不是每一个细节；细节靠级别按需打开。

09 · 结论

事实源单一，投影可替换

回到题眼：界面是事实源的投影。投影可以有很多个 —— 窗口、编辑器、命令行、索引、统计 —— 但事实只能有一份，写者只能有一个，因果必须显式。做到这三条，后面每加一个消费者都只是加一个投影；做不到，每加一个消费者都在增加分歧。

观测因此不属于界面功能，而属于核心设计：它与状态的所有权、协议的形状、权限的边界是同一组决定。准备实现 agent 的人，在写第一个界面之前先把这件事定下来，成本最低。
