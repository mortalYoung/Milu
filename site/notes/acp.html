01 · 定义

headless core 是什么

headless core 指一个不假设自己被谁调用的内核。它持有会话状态、消息日志、模型调用、工具执行与权限判定，把这四件事暴露成服务与事件；它不渲染界面，也不为某个具体客户端留入口。

约束落在三条上：

  1. 依赖面：只允许 node:* 与仓库内的协议层、依赖注入层；不允许 Electron、DOM、socket，也不允许宿主独有的 API。
  2. 所有权：每一份可变状态只有一个服务持有，并且明说自己的开始与结束（create → initialize → dispose）。
  3. 对外形状：只有两种 —— 请求返回一个值，事件描述发生了什么。不存在第三条通道。

第三条是分出「界面」与「内核」的关键：事件只说发生了什么，不说给谁。谁在听、怎么展示、要不要重放，全部属于适配层。

内核描述发生了什么；适配层决定谁听到。

02 · 约束

为什么核心不得感知界面

三条理由，代价依次升高：

  1. 宿主数量。桌面窗口、编辑器、定时任务、命令行是四个接入方。界面一旦写进核心，每增加一个接入方都要回到核心改一次。
  2. 状态归属。界面状态（展开、选中、动画）与持久状态（会话、日志、策略）混在一处，就无法判断哪些该落盘、哪些该丢弃。
  3. 信任边界。渲染进程与外部客户端都不可信。核心若信任调用方传来的路径、命令与档位，权限校验就形同虚设 —— 校验必须发生在核心，而不是在界面。

第二条决定持久化的正确性，第三条决定安全模型是否成立。两者都不是风格问题，因此写成包的依赖规则，让越界成为编译错误而不是评审意见。

03 · 架构

分层与边界

四层，依赖方向单向朝下。

四层的职责与允许的依赖
层 内容 允许依赖
核心层 服务、状态、事件 protocol、di、extension-types
组装层 容器装配 core、extensions、window
传输层 请求注册表与适配器 protocol
表现层 界面、扩展的窗口部件 以上全部

3.1 核心层

服务由 token 标识，容器负责构建：扩展声明自己需要哪些服务，构造函数上的装饰器负责解析，容器是唯一的全局。核心只导出服务与类型，不导出模块级单例 —— 单例一旦成立，初始化顺序就变成隐式约定。

3.2 组装层

全仓只有一处做装配：createBackend 建核心容器，createFrontEnd 建窗口容器。其余包只导出、不组装。「谁和谁被装在一起」是宿主的问题，不是核心的问题。

3.3 传输层

一份请求注册表把方法名映射成一次服务调用，一个传输端口负责把请求送出去、把事件收回来。今天的实现是 Electron IPC：渲染进程发起请求，主进程返回值，事件走单向广播。适配器是唯一知道通道名的地方。

3.4 表现层

渲染进程从应用自定义协议加载，经 preload 桥与主进程通信，contextIsolation 与 sandbox 打开。界面里的每一项功能都来自扩展的声明，外壳不持有扩展代码，也不维护扩展清单。

四层里只有传输层是可替换的。换一次传输，前三层的代码不动。

04 · 扩展点

能力的注入方式

内核不自带功能菜单。功能由扩展声明自己在窗口里的位置：清单写清 id、类型与入口模块，宿主读清单、把入口当模块导入，部件只拿到自己那一份数据。跨进程的扩展由子进程承载，宿主给它的是一份动词清单 —— 注册工具、注册动作、读取设置 —— 而不是服务句柄。

  1. 声明式注册：扩展说的是「我在哪出现」，不是「核心在哪分支」。
  2. 容器装配：扩展声明的服务在启动前注册进容器，生命周期归容器。
  3. 进程隔离：外部安装的扩展运行在子进程，宿主只经协议契约与它来往。

核心的边界因此不是「功能多不多」，而是「能不能被扩展补上」。这一点另有专文，见 Notes · 03《功能都长在扩展上》。

05 · 接入

ACP 接入

5.1 协议定位

ACP（Agent Client Protocol）是客户端与 agent 之间的会话协议，走 JSON-RPC，承载在标准输入输出上。它把角色切成两半：客户端持有界面与用户，agent 持有会话与执行。方法面很窄：

  • initialize：交换版本与能力。
  • session/new、session/load、session/fork、session/list、session/close、session/delete：会话的建立、恢复、派生与管理。
  • session/prompt：推进一轮；session/cancel：中断。
  • session/set_mode、session/set_config_option：调整档位与选项。

窄是设计的一部分：协议只规定会话级的动作，不规定界面长什么样，也不规定 agent 有哪些工具。

5.2 实现方式

接入层是一个新的适配器，不是第二个核心。入口导入组装层的 createBackend，用与桌面完全相同的容器启动核心；适配器把协议请求映射成对既有服务的调用，把核心事件翻译成通知。协议层只负责编解码、错误码与请求响应的配对。

所以「换一个宿主」在这里是一次适配，不是一次重写：会话存储、工具执行、权限策略、模型调用都只有一份实现。

5.3 会话生命周期

  1. new：以客户端给出的工作目录建立会话，返回会话 id。
  2. load：把已存在的会话接回内存。客户端打开历史会话时通常先 load 再 prompt，因此加载过的会话必须按「正在使用」对待，而不是当作只读投影。
  3. fork：复制出一个新会话，此后两者独立演进。
  4. close 与 delete：释放句柄，或移除磁盘数据。移除前要尊重会话自身的锁定状态。

所有权写在会话目录里：谁在驱动、由谁负责终态。带来源标记的会话，其审批与决策归驱动方客户端，本地界面不越权代答。

5.4 能力协商

initialize 的返回值是一份声明集合，客户端据此决定能做什么。形状分三段：

声明集合的三段
段 内容 回答的问题
agentCapabilities 会话恢复、输入形态（图片、内嵌上下文） 会话能不能接回来，输入能带什么
sessionCapabilities 列出、删除、关闭、派生 客户端能对会话做哪些管理动作
_meta.<vendor> 任务、压缩、活动状态、用量，逐项带版本 标准没有覆盖的那部分

规则是「声明即承诺」：客户端只依据声明行事，未声明的能力不该被试探；反过来说，一个键就是一条对客户端的承诺，声明了没实现，比不声明更糟。版本号属于协商内容，不是装饰。

5.5 权限模型

工具越出工作区或触到敏感文件时，核心不自行放行，而是向客户端发起一次审批，选项固定为「本次允许、本会话始终允许、拒绝」。批准结果改变的是策略，不是校验：路径规范化、符号链接解析、只读边界仍然由核心完成。

结果有两种落点 —— 一次调用，或写入会话级档位供后续调用沿用。后者要持久化，并且必须在重连之后依然生效，否则「始终允许」只是一次性的措辞。

5.6 事件语义

内容流由标准通知承载：消息块、工具调用与结果、计划。状态类信号（活动状态、用量）在标准里没有对应位置，走厂商扩展。

这里有一条容易被忽略的约束：状态类事件必须报已确定的状态，而不是正在切换中的值。一次运行结束的通知可能早于内部标志位归位；若此时按「当前是否在运行」现算，客户端会收到「仍在运行」，并一直停在这个状态。适配层知道语义，就应该由它给出状态，而不是让核心的瞬时值决定。

契约规定形状，适配层负责时机。

06 · 必要性

协议化接入的收益与代价

6.1 收益

  1. 一个协议对应多个宿主。编辑器、IDE 插件、命令行工具接入同一份实现，不必为每个宿主写一份私有 IPC。
  2. 复用客户端已有的能力。审批、会话列表、差异展示、终端联动由客户端提供，agent 不重复实现界面。
  3. 边界清晰。协议是唯一契约，排错只需要看消息流。

6.2 标准与扩展的分工

判断依据是「标准里有没有这个能力」，不是「客户端认不认」。会话与内容流走标准；标准没有的部分才放进 _meta，并且逐项标版本。这条顺序不能反：先用扩展补齐，再回头发现标准已有对应能力，等于引入一份协议内的私有方言。

6.3 代价

  1. 协商状态要自己维护。客户端可能不回、可能重连，状态过期后需要重新对齐。
  2. 往返开销。审批与会话管理都是请求-响应，体感取决于客户端。
  3. 可观测性下降。协议没有回执，丢一条通知不会产生错误码。日志与探针因此是必需品。

6.4 适用边界

单宿主、同进程、不需要外部客户端时，直接调用服务比引入协议省事。一旦出现第二个宿主，或者宿主不由自己维护，协议化的总成本就低于维护两份适配。

07 · 结论

内核中性

回到开头那条判断：界面不是主体。今天有两个适配器 —— 桌面渲染进程的 IPC，与编辑器的 ACP —— 它们调用同一个 createBackend，共享同一份会话、工具与权限实现。第三个宿主出现时，需要新增的仍然只是一层适配。

内核中性不是「抽象得好看」，而是一条可验证的约束：换掉接入层，核心代码一行不改。协议化的价值也只在一条约束成立时才成立 —— 否则多一个协议，就是多一份实现。
