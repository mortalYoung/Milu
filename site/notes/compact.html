01 · 定义

Compact 是什么

模型的上下文长度都是有限的。窗口这些年一直在变长，但还是有限，聊得够久总会顶到上限。顶到之后还想继续，就得有机制把上下文整理、删减一遍，让后面的对话还能进行下去。

Compact 就是按某种策略压缩上下文：减少占用，同时尽量保住信息。

不同 harness 的做法不一样。有的直接丢掉上下文，靠检索取回；有的在丢掉之前先写一份摘要。

Milu 把这两件事分开：记忆系统负责整理、存储和检索历史，Compact 只管这一轮往窗口里带什么。

02 · 动机

为什么需要 Compact

记忆系统能保证历史被整理、存储和检索，但它不减少上下文占用。要减少，只能由 Compact 决定这一轮带多少。

Compact 的矛盾在两头：删得越多，丢的信息越多；留得越多，占的窗口越多。信息完整性和上下文占用怎么平衡，就是这个设计要解决的问题。

上下文由系统提示词、工具调用和消息组成。系统提示词是固定的，工具调用和消息占掉剩下的部分。

所以 Compact 要做的事很具体：在工具调用和消息里挑出哪些留下、哪些收起，让固定的窗口装下尽量多的信息。

03 · 设计

如何设计 Compact

Milu 把日志原文当作 SSOT：记忆系统从日志里抽条目、存下来、按需检索；Compact 把日志折叠成摘要，摘要的内容也来自这批条目。

要解决的问题只有一个：

如何将日志折叠成摘要，同时又能够支持记忆系统回溯日志原文？

折叠分三步。第一步定范围：先定留多长的尾巴，再从后往前回溯，找到折叠的起点。

留这一段尾巴，是为了压缩之后上下文里还有刚发生的事，对话接得上。

把尾巴的长度记作 ρ，取窗口减掉输出预留之后的一个比例 k：

k 默认 0.16。k 越大，留下的尾巴越长，进摘要的部分越小。

实测里，1M 窗口、64K 输出预留、k = 0.16，大概能留下十条以上，具体看消息长短。

条数不是固定的：算出预算之后，从最新一条往前按整条消息累加，加到够为止。

第二步是找出需要折叠的区间，也就是除了最近的聊天记录之外，其余需要生成摘要的部分。

日志在这里被切成两段：折叠区间换成摘要，尾巴区间原样保留。

切点按 ρ 估个大概，但落不到固定位置。累加是按整条消息走的，还要避开一次工具调用和它的结果，所以切点会前后挪一点，很少正好落在 ρ 上。

第三步，把折叠区间做结构性替换。

做法是从记忆系统里挑条目、拼成摘要，放回折叠区间原来的位置，前后各加一句：前面说明更早的消息已经归档，后面提醒需要细节时去回读。

挑选有范围：从上次整理到的那一条之后，到这次折叠区间的终点。摘要要覆盖的是这段时间里还在发生的事：起点往前挪，会带进早就结束的内容；起点往后收，又会漏掉这段里的转折。停在折叠区间终点，是因为尾巴还在上下文里，不必再进摘要。

然后是条数。先给 event 留 3 个位置，取最近的三条；剩下的 N − 3 条从其他 kind 里按优先级挑，同级取新的。

3 不是推出来的数。实践里一段区间内真正关键的事件就几条，占摘要的 30% 左右，所以定成 3。

剩下的问题是：什么时候压。

触发有两种：手动和自动。手动是用户要求压一次，在 Milu 里注册成一个 Action；自动由系统按用量判断，不用人管。

自动触发的时机有三个：前两个在 run 之外，第三个在 run 之内。

  • 一次发送之前：用户消息刚写进日志，请求还没发出。
  • 一次续跑之前：恢复一个挂起的 run，同样在请求发出之前。
  • turn 边界：一次工具批次跑完之后、下一次请求发出之前；那一轮的 assistant 消息和工具结果已经落地，投影可以整体换掉。

判断标准就一条：当前用量是否超过 θ。

以 DeepSeek 4.1 flash 为例：128K 窗口、8K 输出预留，算的时候用 128,000 和 8,192；阈值比例 0.8、留白 65,536、保留比例 0.16 都取默认值。

两个候选先算出来：W·r 给出 102,400，W − O − H 给出 54,272。取小的，θ 落在 54,272，这一轮装到 54,272 就该压了。

三个数凑满整窗：54,272 的历史、65,536 的留白、8,192 的输出预留。这条线只到窗口的 42%，跟「装满才压」差得很远，差的就是留白。在这个窗口上，65,536 占 51%。

留白因此做成了设置项。调到 16,384，W − O − H 变成 103,424，反过来比比例的 102,400 大，θ 升到 102,400，占窗口的 80%，压缩回到「快满才压」。同一个模型，只动留白，触发点从 42% 挪到 80%。

54,272 再切成两半。尾巴按 (W − O) × 0.16 留，119,808 × 0.16 = 19,169，折叠区间是前面 35,103。一次读文件的结果常有几千 token，19,169 只够最近几轮，更早的读取都进了折叠区间。

放进一次具体的会话：agent 改一个模块，读几个文件、跑两次测试、改两处代码。系统提示词和工具定义先占一截，剩下的由消息和工具结果填，几十次工具调用就摸到 54,272。触发落在 turn 边界，那次工具结果刚写进日志、下一轮请求还没发出，前半段换成摘要，最近几轮原样留着。接着改，模型不用重读刚才那些文件。

3.1 摘要为什么不由模型写

Compact 自己写摘要，等于对同一段历史再概括一次。记忆抽取已经做过一遍：那段对话被整理成一条条带原文引用的记忆。

  • 再概括一次不会更准，只会在已有的结果上再丢一层。
  • 概括本身有损。模型改写一遍，措辞、数字、指代都可能变，事后也不知道丢了什么：摘要里没有的东西，分不清是被判为不重要，还是根本没读出来。

复用已有条目就没有这道损失。摘要条目全部来自记忆系统，压缩只决定挑哪几条、按什么顺序排，一个字不改。

  • 不重复劳动：每次压缩省一次调用、一段延迟，也省一次输出 token。
  • 损失可逆：每条摘要挂着记忆系统的 id，能回溯原文。
  • 只有一套说法：摘要条目和记忆是同一份内容，不会出现两处说法不一。

能这么做，前提是两者共用同一份日志：抽取读的条目和压缩遮蔽的条目是同一批。

3.2 为什么不等撞线才压

很简单，如果等撞线才压，极有可能连回答的位置都没有。

一次请求的窗口预算里不只有历史。这一轮的回答、工具调用的参数，都要塞进同一块空间。历史顶到窗口，回答就没地方放，请求会被拒；就算勉强发出去，模型也只能写出半句话。

θ 就是从这头反推的：扣掉输出预留 O 和留白 H，剩下的才是历史能占的高度。所以 θ 触发时，窗口里还空着 65,536 + 8,192 = 73,728 个 token。

撞线之后也不是没救：请求因为超出窗口被拒，可以压一次再重试。机会只有一次，而且这一轮已经白跑。提前压，是把这类失败挡在前面。

代价是压得更频繁，尾巴更短，更多内容进摘要。留白不是越大越好：128,000 的窗口上，默认的 65,536 就占 51%，触发点被拉到 42%，这也是它被做成设置项的原因。

04 · 小结

回头看那个问题

回到第三章开头那个问题：如何把日志折叠成摘要，同时又能够支持记忆系统回溯日志原文。

前半句的答案：日志没动，动的是投影。遮蔽的条目从上下文里剔掉，摘要插成一条 user 消息，检查点里记下这次遮了哪些条目、给了什么摘要。

后半句的答案：摘要当索引，原文当底本。摘要条目全部来自记忆系统，每条挂着 atom，atom 记着来源条目的编号，按 id 就能取回逐字原文；前言说明更早的消息已归档，尾注提示需要细节时回读。

两半能对上号，是因为共用同一份日志：压缩遮蔽的条目和记忆抽取读的条目是同一批，检查点里的遮蔽清单就是这次摘要的覆盖范围。
