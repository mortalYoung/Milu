01 · 定义

记忆系统是什么

Agent 记忆系统从 agent 与用户的互动里取知识，把知识结构化地存下来，再以上下文的形式交还回去，让下一轮回答好一点。

公式里这三项就是记忆系统的三个部分：源数据、结构化数据、检索。

S 是源数据，互动留下的原始记录：消息、工具调用与返回、上传的文件，以及接入的邮件、日历、工单等外部内容。多数应用把它存成只追加的事件表或消息表，每条带 id、时间戳和会话 id，先全量落盘，之后再处理。

D 是结构化数据，从源数据里抽出的、能被程序检查的知识：事实、实体、偏好、待办和发生过的事件。常见形式有几种：关系表、用户画像的键值对、JSON 文档、图数据库的点边，也有把「文本块 + 元数据」放进向量库的。形状由 schema 决定，写侧负责去重与合并冲突。

Q 是检索，给定当前问题，从结构化数据里挑出一小段，按 token 预算放回上下文，需要细节时再回看源数据。常见实现有 SQL 过滤、全文检索、向量相似度加元数据过滤，或者混合后再 rerank；输出是按相关度或时间排序的一小段。

三项互相牵制：源留得越全，抽取越贵，检索也越难挑。产品之间的差别，大多在这三处的取舍上。

然而对话一长，源只增不减，结构越抽越多，检索却要在更多东西里挑出更短的一段。这套做法还能撑多久？

02 · 动机

为什么需要记忆系统

对话会越来越长，而模型这一侧有两个不会跟着放宽的限制。

  1. 上下文是一个固定的 token 数。装得下的就那么多，装不下的那一部分，这一轮就等于不存在。
  2. 注意力是有限的资源。塞进去的内容越多，模型在长上下文里找到那一条具体事实的能力反而越弱——不是没放进去，是放进去了也找不准。

记录可以无限增长，这两样不能。

记忆系统的必要性就落在这处不对称上：不断增长的历史记录，同不会增长的上下文窗口之间的矛盾。

那么基于这个不对称点，记忆系统真正要做的事有：

一是克制地记录互动。它不搬运整段对话，只留下之后还会用到的部分：做过什么决定、改到哪一步、哪些约束仍然有效。记录有边界，条数、长度、时间都有上限，也有出处，能指回原始消息。

标准定得太紧，重要的事就再也找不回来；定得太松，记录会退化成第二份对话记录，读不动也查不快。记什么、留多久、以什么形状留，是第一个要权衡的地方。

二是把重复的做法沉淀成方法。同一类任务做过几次，步骤、判断点和踩过的坑就稳定下来，可以写成一份流程。下次遇到同类任务，agent 不必重新摸索，也能预判下一步往哪走。

抽象程度得挑：抽得太细，换个项目就不适用；抽得太粗，执行时还得重新摸索。方法一旦写死，错的做法也会跟着变成惯例，所以它还得能改。

三是记住偏好。语气、篇幅、常用工具、不喜欢的做法，说一次就该生效，不用每轮重申。麻烦在于偏好会变，也会被单次情绪带偏：记老了会冒犯，记少了要反复确认，记太宽又会盖过具体场合的要求。偏好记准了，同样的输出不用反复调试，agent 才谈得上好用。

三处都没有标准答案。记录宽一点会占地，方法具体一点会过时，偏好记全一点会僵化。剩下的事是在三处各挑一个位置：留什么、抽到多细、记到什么程度。

03 · 设计

如何设计记忆系统

Milu 把记忆分成两个平面。会话日志是档案：逐字、只追加，任何一轮说过的话都还在里面。Atom、SOP、Persona 是索引：有损、去重、带结构，负责回答「去哪读」，不负责复述全文。

索引按用途分三层：Atom 记互动，SOP 记方法，Persona 记偏好。三层里答不了的细节，回档案里读原文——索引给地址，档案给原话。

3.1 Atom

先要定的是记什么。

多数记忆系统用的是 RAG：把对话切片、算向量、按相似度取回，比如 Mem0。

  • 写得不准。该记的偏好和长期事实可能漏掉，琐碎信息反而留下；换个说法，抽取结果也可能不同。重复与矛盾的记忆仍会留下：先「住在上海」、后「搬到北京」，系统要花时间和语境才判断得出这是更新还是冲突，重复的那份还一直占着上下文。
  • 改得不清楚。新事实可能新增、合并或改写旧记忆，用户看不出改了什么、旧事实是否还有效、系统为什么这么处理。
  • 取回了什么，说不清。检索返回了哪些记忆、为什么认为它们相关、回答最终用了哪些证据，都不一定透明。

Milu 的做法是从对话里整理出带 kind 的结构化记录，每条挂一层 metadata：能回溯原文，也能按它归类、整理。

kind 怎么分，直接决定后面检索和归纳顺不顺手，所以要先定下来。

Milu 只留六类，每一类对应一种场景。

六类 atom 与各自的场景
kind 场景
attribute 稳定的属性，比如设备系统、居住城市、通勤时长
event 一次发生的事，比如买了什么、参加了什么活动、发布一版
reference 会被回头用的东西：清单、地址、参数、方案，也包括你按需产出的成品
preference 对某类情境的取舍，比如回复要短、晚上不排会
instruction 长期规则，比如提交前必须跑检查
update 旧值换成新值，比如换了工作、改了常用语言

这六类各自对应一种不单独存就会丢、或者会混的情况。

  • attribute：把不随时间变化的属性和发生的事分开。否则「通勤 40 分钟」会被反复记成事件，越积越多。
  • event：必须带发生时间，才能回答「上个月买了几次」这类统计。没有它，购买和参与只能折进偏好或摘要，之后就数不出来。
  • reference：指向会被回头用的东西——清单、地址、参数，或者你按用户要求产出的成品（剧本、文章、报告、代码）。它有来源、会过期，和用户自己的事实不是一回事。
  • preference：带方向和场合。「回复要短」只在某些场景成立，缺了场合就会变成硬规则。
  • instruction：和偏好分开，因为它是约束，不是倾向；违反要算错，不是「不太喜欢」。
  • update：记录替换关系，让当前值唯一。没有它，同一个属性会同时挂着几个「有效」的值。

Milu 的体会是，事无巨细地记并不划算：类目越多，写错和漏标的机会越多。决定记什么的同时，也在决定舍弃什么。

  • decision 与 issue：本质是带结果的事件，并进 event，不再单列。
  • scene：曾经作为一层做聚合，后来删掉；聚合结果说不清来自哪几条互动，也没法校验，改由 SOP 与 Persona 从 atom 蒸馏。
  • task：属于会话过程，不是长期记忆，存下来只是待办列表的副本。
  • emotion：单次情绪不可靠，容易把一次抱怨误判成偏好。
  • summary：一次性文本，不能校验也不能更新，正是 RAG 那条路。

按这套结构实现之后，Milu 在 LongMemEval 的 100 题上判题通过 89/100 = 89.0%；同样的窗口、同样的模型，只看最近 10 条消息的对照组是 21/100 = 21.0%。

按能力拆开，四类回忆题都在 80% 以上，abstention 与对照组基本持平（18/20 对 17/20）：

100 题分桶对照
能力 只看最近 10 条 带记忆
single-session 3/20 20/20
multi-session 0/20 18/20
knowledge-update 1/20 17/20
temporal 0/20 16/20
abstention 17/20 18/20

对照组的 21.0% 几乎全在 abstention 那一栏：需要回忆的四类合计只有 4 分。也就是说，不接记忆的时候它并不是「记得少」，而是几乎答不出任何需要从历史里捞东西的题，能拿分的只剩「该说不知道的时候说了不知道」。

除此之外，atom 上还挂着一层 metadata：来源消息的编号、事件发生的时间、写入时间，以及它属于哪一类。这层信息不参与检索排序，却会跟着检索结果一起返回：读到一条 atom，就同时拿到它由哪几条消息支撑。这些编号不是事后核对用的坐标，而是下一步的入口——需要逐字细节时，按它回读原文。

由此定下一条取舍：reference 只描述与指向，不承载正文。一份剧本、一篇报告有几千字，塞进 atom 会让每次检索都变重，而且「该摘哪几句」没有答案。做法是记下「有这件东西、里面有什么」，把可检索的要点放进 items，正文留在档案里，靠编号指回去。

举个日常的例子。用户在杭州工作时聊过自己的通勤，两年后说起公司把他调去了上海。库里不会把「杭州」抹掉，而是留下一条 update：旧值杭州、新值上海，变更时间是后来那次对话。点开这条 atom，能看到它挂着的两条来源消息，一条是当年的入职闲聊，一条是这次的调动说明；哪一天发现城市判断错了，顺着编号回去读原文，就能改回来。

3.2 SOP

atom 的记录是离散的：一条对着一个时刻、一件事，回答「发生过什么」很合适，回答「这类任务一般怎么做」就不够了。同一类任务做过几次，才能看出哪些步骤固定、哪里要判断、哪一步最容易出错。这层总结得再做一次。

SOP 就是这次总结的产物：从若干条 atom 里抽出可复用的流程，写成一篇文档。它不替代 atom：先把方法摆出来，细节回 atom 里找。

文档的章节固定为五节，每一节各管一段职责。

  • Purpose：这份流程解决什么问题，读完这一段就知道该不该往下看。
  • When：一句话说明什么请求该用它，也是索引里常驻的那一行。
  • Procedure：编号步骤，一步一个动作；判断点写成「若…则…」，检查点写成「确认…」。
  • Checklist：执行前后要确认的事项，防住「步骤都做了，结果没验证」。
  • Pitfalls：踩过的坑，最多 5 条；这一节决定下一次能不能少走弯路。

章节之外还有几条硬约束：标题至多 24 字，When 一句话至多 80 字，Procedure 至少两步，证据至多 30 条；正文每一步都要引用证据里的 atom 编号，落不到任何 atom 上的步骤会被拒绝。

SOP 也有上限：20 篇。索引一行一篇、常驻在上下文里，篇数再多，光索引就要占掉一块预算。

3.3 Persona

persona 同样是从 atom 里再收一次，只是对象从任务换成了人。atom 里散着「回复别太长」「晚上别排会」「别用表情」这类碎片，单看一条只说明某一次偏好；要让 agent 知道「这个人希望被怎样对待」，得把它们合到一页上。

收出来的是一页文档，只从偏好、指令和角色类的 atom 里取料，其余细节留在 atom 层按需召回。它只回答一个问题：接下来该怎么和他说话。

文档只有两节，各自管一件事。

  • 关系：谁在用、通常怎么协作、有哪些长期约束，至多 4 行。
  • 口味：界面偏好与工作节奏，至多 6 行，其中界面与节奏各至多 3 行。

每一行都要注明来自哪条 atom，带上编号和日期；属于别处的内容不写，比如绝对路径、提交编号、任务进度、分支状态。落不到 atom 上的话，宁可删掉。

为了每轮都能进上下文，persona 限 1,200 字。写不下只能删，留下的就是会影响行为的那部分。

3.4 抽取的契约

atom 由模型从对话里抽，抽什么、抽多少，不能全凭它当时的判断，所以要有一条可验收的契约：读过的每一条，要么有原子背书，要么明确说「这里没有值得记的」，并给出理由。

落地是两道闸。一道在轮次末尾：条目覆盖率或字符覆盖率低于一半、且缺口超过二十条时，引擎带着这批缺口重扫一次；只补一次，覆盖率是触发器不是分数，逼到百分之百只会白烧预算。另一道在断点上：水位只在接受时推进，补扫不推进，否则下一轮会认为这段已经做完，缺口被永久埋掉。

三个索引层各看各的料，不共享一份输入。SOP 只读 event——流程来自重复发生的事，偏好和规则属于 persona 与项目约定；persona 只读 preference、instruction 和角色类的 attribute。两边都分页读：一次一页、每次运行有上限，读到哪就把水位推到哪，不把整段历史灌进上下文。

写入同样按契约来。YAML header 拆成参数、正文单独传，长度与形状只校验正文，所以不可能出现格式坏的 frontmatter；SOP 的每个编号步骤都要引用 evidence 里的 atom，落不到任何 atom 的步骤会被拒绝；库里没有文档时，读取回答「还没有」，而不是「找不到」。这些约束的共同点是：能由程序判定的，就不交给模型临场发挥。

3.5 检索

三层都建好之后，最后一个问题是每一轮到底取什么进来。窗口有限，全塞进去等于没有检索；取错了，前面的结构再整齐也白搭。

atom 的取法是结构化过滤：按种类、主体与属性、时间区间、字面词组合查询，按命中与时间排序，一次返回一页。上限写在工具里：一次最多 30 条，单条细节 400 字，一次回答 6,000 字；超出直接拒查，并给出在场的主体、日期跨度和翻页建议，让模型自己把查询收窄。

读取方是一个会改写查询的模型，不是一个只查一次的搜索框，所以字面匹配比相似度更合适：它能预测「换个词会怎样」，收窄建议把「查不到」变成「下一次怎么查」。这两件事相似度分数给不了。代价是召回偏保守。

结果里还有两条规矩：被取代的记录默认隐藏，一条更新读起来是当前的一个值；同一个主体和属性有多个活值、中间又没有更新链时，回答会说出来，而不是挑一个。

原子答不了的细节，回档案里读。检索因此有两档：scope="entries" 按词去原文里找，返回命中片段与条目编号；rawIds 按编号把原文取回来。取回不是整篇倾倒，而是按预算开一个窗口——一次 8,000 字封顶，可以指定从第几个字续读，也可以要求围绕命中的词开窗。回复的头一行写清「这句话是几月几日谁说的」，长度和剩余部分一并给出，再长的消息也只是多读一次，不会读不到。

原文检索的打分与原子不同：原子按字面命中与时间排，原文按「命中了几个不同的词」排，命中越多越靠前，出现次数作次要权重。原因是查询往往是一整句话，要求整句都出现，就只有提问本身能满足——提问里恰好塞满了关键词，于是它永远排第一。所以检索前先把当前回合排除掉。

最后一条是口径。问到「你之前说过什么、推荐过什么」时，档案是权威：先引用，再把异议接在后面，不能用修正替掉回忆。模型很容易在这里走歪——它读到一句与自己知识相背的旧话，会把「我说过这句」和「这句对不对」合成一个问题，然后回答「我说错了」。分野在于：回忆类问题的真值条件是记录，不是世界。

常驻的部分更简单。SOP 只放一行一篇的索引，正文按需翻页；persona 整页随提示注入，带一个内容指纹，完全相同的提醒不会注入两次，变化过的则一定注入。压缩之后全部重新注入，因为压缩把原来的消息收起来了。

窗口预算可以写成一行加法。

压缩时按覆盖范围选档位。全量覆盖时，摘要里写「更早的消息已归档到长期记忆」，再加至多十条摘要，末尾一句「需要细节就回忆」；只覆盖一部分时，切到覆盖索引之前的最后一个用户轮次，其余原样保留；没有覆盖时，退回最近的一问一答，并说明日志里还有其余部分。十条摘要按价值排序：三条留给最近的事件，其余按更新、偏好、指令、属性、参考排。

三层共享同一份 atom，上层必须引用下层，所以每条结论都能回到原文核对；核对不是终点，顺着编号回读原文才是。上限也写在各层里：六类 atom、20 篇 SOP、一页 1,200 字的 persona，以及一次检索的字数预算。留什么、留多少，都是设计时定死的，不留给模型临场发挥。
